一、先修了两个"隐形的根因"（与本次需求无关但必须先修，否则兜底会变成常态主源）

根因1：TDX 端点没有失效转移（解释了历史"上午有数据、下午就降级"）

  • 本会话 mcpServers 里同时存在 tdx-finance(7df0c7d4) 与 tdx-connector(424fab19) 两个 tdx 键。
  • tdx-connector 间歇性 401（同一会话内一次成功、下一次 401），而旧 zt_mcp_client.py 只取

"字典里存在的第一个键"(tdx-connector 在候选首位) → 把 401 直接抛给上层 → 表现为随机降级。

  • 同一个 401 还影响 zt_trade_cal.py（打印 [WARN] TDX 交易日历不可用：HTTP Error 401）。
  • 修复：zt_mcp_client.py 增加 get_tdx_endpoints()（返回全部候选，不发网络）+ get_tdx_endpoint(probe=True)

逐个 initialize 探测、取第一个可用并进程内缓存；新增 open_tdx_client() / get_tdx_info() / reset_tdx_cache()。
TDX_SRV_CANDIDATES 改为 ("tdx-finance","tdx-connector")（新名在前）+ 任意含 tdx 键模糊兜底。
7+ 处调用点（zt_trade_cal / zt_pipeline_fetch / zt_925_review / zt_tdx_features / zt_fetch_run / sb_backtest_v2）无需改动即受益。
实测：注入 2 个坏端点（404 + 拒连）夹在真端点之前 → 正确跳过并选中可用端点。

根因2：腾讯 ifzq.gtimg.cn 的日K路径被 WAF 拦（501）

  • curl https://ifzq.gtimg.cn/appstock/app/fqkline/get?... → HTTP 501 + waf.tencent.com 拦截页。

同主机的 分钟K(mkline) 正常；web.ifzq.gtimg.cn、proxy.finance.qq.com/ifzqgtimg 均 200。

  • 修复：TX_KLINE_HOSTS 三入口失效转移 + 熔断（某入口某路径确认不可用后本进程不再重试）。

另在 rank10d 里按代码轮转入口分散单主机压力。熔断后耗时 49.1s → 32.7s（恢复原水平），

二、nontdx_src.py 接入 TDX 保底层

策略开关：--tdx auto|off|force（默认 auto）；--no-tdx-enrich；环境变量 NONTDX_TDX / NONTDX_TDX_ENRICH。

  • auto = 主源失败/返回空 → TDX 兜底；主源拿不到的字段 → TDX 补缺
  • off = 完全不碰 TDX（旧行为，已验证主源挂了就 exit 2 硬报错）
  • force = TDX 优先（仅排错/对比）

新增 TDX 能力封装：tdx_quotes / tdx_indices / tdx_kline / tdx_screener / tdx_emotion /
tdx_rank10d / tdx_sectors / tdx_fundflow + 通用 with_tdx(primary, fallback, what)。
输出统一加溯源字段：src / tdx_fallback / fallback_errors / tdx_enriched_fields /
tdx_probed / tdx_client_ok / tdx_error。

新增 doctor 子命令：一次探测「非TDX主源(4项) + TDX 兜底」，给 verdict，供自动化第0.5步用。
